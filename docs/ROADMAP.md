# Roadmap

This roadmap is deliberately small. Work through milestones in order. Each milestone should leave the project usable and easy to continue.

## Milestone 0 — Repository foundation

- [x] Define product purpose, technical boundaries, and initial MVP
- [x] Create README, AGENTS, roadmap, and gitignore
- [x] Commit repository foundation

## Milestone 1 — Data proof of concept

- [x] Scaffold Astro + React + TypeScript in the repository root
- [x] Add basic scripts for local development, build, and type checking
- [x] Select one representative location: Heraklion, Crete
- [x] Verify NASA POWER climatology endpoint and temperature parameters against current documentation
- [x] Fetch data for 12 months using a documented historical period
- [x] Validate units, missing values, and returned metadata
- [x] Normalize data into a typed JSON format; record source and period
- [x] Display a basic 12-month temperature table or chart
- [x] Ensure the static site builds successfully

**Done when:** a visitor can open a static page and inspect 12 real, source-labeled monthly temperature values for the selected location. No need for polished design.

### Milestone 1 decisions and limitations

- The static data is generated by `scripts/fetch-destinations-climate.mjs`; visitors do not make live NASA POWER requests.
- It uses NASA POWER `T2M` (mean temperature at 2 metres), in degrees Celsius, for January 1991–December 2020. The response identifies MERRA-2 as its source.
- The normalization step rejects missing values (the API response's `-999` fill marker) rather than substituting zero. Its test fixtures are explicitly synthetic.
- The values describe NASA POWER's returned representative grid point near Heraklion, not every part of Crete, and they are historical climate averages rather than a forecast.
- The initial validation covered one temperature request; Milestone 2 independently validated the precipitation and solar-radiation parameters.

## Milestone 2 — Curated destinations and filters

- [x] Define stable destination metadata and representative coordinates
- [x] Curate an initial 10 destinations, then expand toward 30
- [x] Add validated monthly precipitation and solar-radiation metrics
- [x] Implement month, temperature, and rainfall filters
- [x] Show responsive destination cards and meaningful empty states
- [x] Add data validation tests

### Milestone 2 decisions and limitations

- The initial curated set contains 10 stable destination IDs. Their labels and representative request coordinates live in `scripts/destinations.mjs`; generated climate records are kept separately in `src/data/destinations.json`.
- The filters operate on the selected month's historical mean temperature and estimated monthly precipitation. They run in a small React island; the initial card list is still rendered into the static HTML.
- NASA POWER `PRECTOTCORR` is returned in mm/day. The displayed and filtered monthly precipitation value multiplies that daily climatological average by the number of calendar days in the selected month. It is an amount of precipitation, not a count of rainy days.
- `ALLSKY_SFC_SW_DWN` is displayed as all-sky surface shortwave downward irradiance in kWh/m²/day. It is a solar-radiation indicator, not hours of sunshine.
- The 1991–2020 requests report SRB, SYN1DEG, and MERRA-2 provenance. These data describe representative grid points and should not be read as local forecasts or precise conditions across an entire destination.

## Milestone 3 — Comparison and destination pages

- [x] Compare two destinations across months
- [x] Generate static destination pages from slugs
- [x] Explain local climate variation and the limitations of historical averages
- [x] Add methodology and data attribution pages

### Milestone 3 decisions and limitations

- The comparison table lets visitors choose two different destinations and compares monthly historical temperature and estimated rainfall. Solar radiation remains available on each destination page.
- Destination pages are generated statically from the stable destination IDs in the generated climate records. Ten destination pages and the methodology page are part of the build; no server routing or runtime data fetch is used.
- Every destination page explains that the requested and returned API coordinates identify a representative point, not an entire region. It also distinguishes historical averages from a forecast for a particular trip.
- The methodology page records the metric definitions, precipitation conversion, data attribution, and missing-value behaviour. NASA POWER data-use and licensing terms remain a pre-public-launch review item.

## Milestone 4 — Data quality and useful presentation

- [ ] Add average daily maximum temperature (`T2M_MAX`); verify NASA POWER parameter availability, units, and monthly climatology semantics before use
- [ ] Display mean temperature and average daily high with distinct, accurate labels
- [ ] Add simple 12-month climate visualizations without introducing unnecessary dependencies
- [ ] Validate all generated destinations and months for missing values, ranges, and consistent units
- [ ] Ensure invalid or missing measurements are never silently shown as zero or valid observations
- [ ] Document the historical reference period, data source, and metric definitions consistently across the site
- [ ] Verify NASA POWER data-use conditions and required attribution before commercial use or launch
- [ ] Confirm filters and comparisons use the same metric definitions as destination pages
- [ ] Test the finder, comparison tool, and destination pages on mobile screens

**Done when:** visitors can compare destinations without confusing historical means, average daily highs, monthly precipitation, or solar radiation. All displayed data is validated and clearly labeled.

## Milestone 5 — SEO and public launch

- [ ] Create useful, non-duplicative monthly landing pages with meaningful destination comparisons
- [ ] Add unique page titles, meta descriptions, canonical URLs, sitemap, and robots.txt guidance
- [ ] Add relevant internal links between monthly pages and destination pages
- [ ] Check accessibility, mobile layout, performance, and broken links
- [ ] Verify that important destination content is present in generated HTML without client-side JavaScript
- [ ] Confirm climate data attribution, licensing, and rights to any destination imagery
- [ ] Deploy to a free static host and verify the production build and URLs
- [ ] Connect Google Search Console, submit the sitemap, and check indexing status
- [ ] Add minimal privacy-conscious analytics if desired; assess consent requirements before adding third-party tracking

**Done when:** the site is publicly accessible, usable on mobile, technically indexable, and transparent about its data sources and limitations.

## Later, only if there is evidence of demand

- More destinations and regions
- More nuanced climate indicators, if reliable sources exist
- Improved comparison and discovery UX
- Optional monetization after evaluating licensing and privacy requirements

## Explicitly out of scope for MVP

Live forecasts, flight prices, hotel bookings, user accounts, saved trips, a database, AI recommendations, and interactive maps.
